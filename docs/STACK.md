# ใช้ ETL ช่วยประมวลผลและคำนวณให้ AI ได้ไหม

**ได้ และควรใช้ แต่ใช้ในรูป "ขั้นตอน ETL ที่เบา" ไม่ใช่เครื่องมือ ETL ตัวใหญ่**

## ETL คืออะไรในโปรเจกต์นี้
- **Extract:** ดึงข้อมูลดิบจาก `captures` + `analyses` + `batches` + `stations`
- **Transform:** คำนวณอายุผัก, นับอาการต่อสถานี/ล็อต/วัน, อัตราภาพถูกปฏิเสธ, ค่าเฉลี่ยเคลื่อนที่ 7 วัน, เทียบล็อตอายุเท่ากัน, ตรวจค่าผิดปกติ (anomaly), ทำความสะอาดข้อมูล (ตัดซ้ำ, ตัดภาพที่ไม่ผ่านคุณภาพออกจากสถิติ)
- **Load:** เขียนผลลง `daily_stats` (และตารางสรุปอื่น) แล้วให้ API สาธารณะ, กราฟ, และ AI อ่านจากตารางที่สรุปแล้ว

## ช่วย AI ได้อย่างไร
| ปัญหา | ETL ช่วยอย่างไร |
|---|---|
| ประวัติ 100 วันยาวเกินส่งให้ AI | ส่งแค่ตัวเลขสรุป ~1–3 พัน token แทนข้อมูลดิบหลายหมื่น token (ประมาณการ) |
| AI คำนวณเลขผิดได้ | ให้โค้ดคำนวณ แล้ว AI แค่เล่าและอธิบาย |
| ผลต่างวันไม่ตรงกัน/ซ้ำ | ขั้น Transform ทำ idempotent: รันซ้ำได้ผลเดิม |
| ต้องวัดความแม่นยำ | ETL ส่งออกชุดข้อมูลที่ติดป้ายแล้ว (ภาพ + label ที่คนตรวจ) ไปใช้เทียบโมเดลต่างเจ้า |
| ต้นทุน AI | สรุปครั้งเดียวต่อรอบ/วัน เก็บผลไว้ใช้ซ้ำ ไม่เรียก AI ทุกครั้งที่เปิดหน้า |

## สิ่งที่ ETL **ไม่ได้ทำ**
- ไม่ได้แทน AI ในการ**ดูภาพแล้วบอกโรค** (ขั้นนั้นต้องใช้โมเดลมองภาพ)
- ไม่ได้ทำให้ผลวิเคราะห์ภาพแม่นขึ้นเอง (ทำได้อย่างมากคือกรองภาพเสียก่อน ซึ่ง OpenCV ทำอยู่แล้ว)
- ถ้าผลวิเคราะห์ภาพพื้นฐานผิด ตัวเลขสรุปก็ผิดตามไปด้วย (garbage in, garbage out)

## เครื่องมือที่เลือกได้ (เรียงตามความเหมาะกับขนาดข้อมูลนี้)
ข้อมูลของ NEXXA เล็กมาก (ราว 1,800 แถวใน 100 วัน ตามสมมุติฐาน 3 สถานี × 3 มุม × 2 รอบต่อวัน)

| ตัวเลือก | เหมาะไหม | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **โมดูล Python + SQL ในโปรเจกต์ (แนะนำ)** เช่น `stats.rollup` ที่วางแผนไว้ในงาน 6 | ✅ เหมาะที่สุด | ไม่มี dependency ใหม่ ทดสอบด้วย pytest ได้ ขึ้น hosting ฟรีได้ | ต้องเขียนเอง |
| SQL view / materialized view ใน PostgreSQL | ✅ เสริมได้ | เร็ว ประกาศง่าย | SQLite ไม่มี materialized view, ผูกกับฐานข้อมูล |
| pandas / DuckDB สำหรับวิเคราะห์ออฟไลน์ | ✅ สำหรับการวิเคราะห์/ส่งออกชุดข้อมูลประเมินผล | ทรงพลัง | ไม่ควรรันบน hosting ฟรี (กิน RAM) |
| dbt (แปลงด้วย SQL) | ⚠️ เกินจำเป็นตอนนี้ | โครงสร้างดี มีเทสต์ข้อมูล | ต้องตั้งค่าเพิ่ม ใช้กับ Postgres เป็นหลัก |
| Airflow / Prefect / Dagster | ❌ เกินจำเป็น | จัดตารางงานซับซ้อนได้ | หนัก ต้องมีเซิร์ฟเวอร์แยก ไม่เหมาะ hosting ฟรี |

## วิธีรันขั้นตอน ETL บน hosting ฟรี (ข้อควรระวัง)
hosting ฟรีมักหลับเมื่อไม่มีคนเรียก ตัวตั้งเวลาในโปรเซส (เช่น APScheduler) จึงอาจไม่ทำงาน แนวทางที่ผมแนะนำ:
1. **ทำแบบเพิ่มทีละส่วนหลังรับภาพเสร็จ** (incremental) — อัปเดตแถวของวัน/สถานีนั้นทันที
2. **ไล่ตามให้ทันตอนเริ่มระบบ** (catch-up) — คำนวณวันที่ตกหล่น
3. **ตัวตั้งเวลาภายนอก** (ถ้าต้องการ) เรียก endpoint ที่ป้องกันด้วย device key หรือ admin เพื่อสั่งสรุปรายวัน
ทุกขั้นต้องเป็น **idempotent** (รันซ้ำแล้วได้ผลเหมือนเดิม) — ข้อควรระวังที่พบแล้ว: ตาราง `daily_stats` กันซ้ำไม่ได้เมื่อ `batch_id` เป็นค่าว่าง (SQL มองแต่ละ NULL ว่าไม่ซ้ำกัน) ต้องเช็กซ้ำเองด้วยการค้นก่อนเขียน

## สรุปคำแนะนำ
ใช้ ETL แบบเบาเป็นโมดูล Python + SQL ในโปรเจกต์ (ตามที่วางไว้ในงานที่ 6) แล้วให้ AI สรุปผลจากตัวเลขที่คำนวณแล้ว หากข้อมูลโตมากหรือมีหลายโรงเรือนค่อยพิจารณา dbt / Postgres materialized view ภายหลัง
