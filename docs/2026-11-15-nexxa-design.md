# NEXXA — Design (ร่าง รออนุมัติ)

ที่มา: `Requirements/NEXXA_System_Overview.pdf` + บทสนทนา 2026-11-15
ป้าย **[คุณเลือก]** = ผู้ใช้ตัดสินใจเอง, **[ผมเลือก]** = ข้อเสนอของผู้ช่วย ยังแก้ได้

## 1. เจตนาและเหตุผล
รถหุ่นยนต์เดินตามเส้นในโรงเรือนผักกางมุ้ง วิ่งผ่าน 3 สถานี ถ่ายใบผัก ให้ AI ตรวจอาการ แสดงผลบนจอรถ แจ้งเตือนเมื่อพบอาการเกินเกณฑ์ และสรุปรายงานประจำรอบ
ผู้ใช้: เจ้าของ/ผู้ดูแลโรงเรือน ต้องการรู้ปัญหาโดยไม่ต้องเดินตรวจเอง

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / สิ่งที่ถือว่าล้มเหลว
**เป้าหมาย**
- ครบวงจรต่อสถานี: ถ่าย → กรองภาพ → Claude วิเคราะห์ → บันทึก → แสดง/แจ้งเตือน
- ขยายจาก 1 เป็น 3 สถานี **[คุณเลือก — ตามเอกสาร]**
- ตรวจ 2 อาการเท่านั้น: **ใบเหลือง** และ **จุดสีน้ำตาล** ในโรงเรือนกางมุ้ง **[คุณเลือก]**

**ไม่ใช่เป้าหมาย**: ตรวจโรค/แมลงอื่น, ตรวจนอกโรงเรือน, ครอบคลุมทุกใบ (กล้องเห็นเฉพาะใบในเฟรม), แอปมือถือ

**ล้มเหลวแม้ทำงานได้**: แจ้งเตือนผิดบ่อยจนไม่มีใครเชื่อ, ภาพเสียถูกส่งไปเสียค่า Claude, ผลวิเคราะห์ผูกผิดสถานี/รอบ

## 3. ข้อจำกัด
- Python Server รันบน **hosting ฟรีบนอินเทอร์เน็ต** **[คุณเลือก]** → ESP32 และจอรถต้องออกเน็ตได้
- AI ทั้งหมดใช้ **Claude** (วิเคราะห์ภาพ, สรุปรายงาน, ตอบคำถาม) **[คุณเลือก]** — Claude API ไม่ฟรี
- ข้อจำกัดของ hosting ฟรี (จากความจำ ต้องตรวจก่อนเลือกเจ้า): Server อาจหลับ, ดิสก์อาจถูกล้าง, CPU/RAM น้อย, บางเจ้าจำกัดการเรียกออกเว็บภายนอก
- ยังไม่ทราบว่าโรงเรือนมี Wi-Fi ออกเน็ตเสถียรไหม (คำถามที่ยังไม่ได้รับคำตอบ)

## 4. แนวทางที่พิจารณา
| | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A** | ESP32-CAM ล้วน ถ่ายและส่งภาพเองผ่าน Wi-Fi; จอรถ = แท็บเล็ต/มือถือเปิดเบราว์เซอร์ | ถูกสุด ไม่มีคอมพิวเตอร์บนรถ | กล้อง OV2640 คุณภาพต่ำ อาจมองไม่เห็นจุดน้ำตาลเล็ก |
| B | Raspberry Pi + กล้อง USB/Pi Camera บนรถ | ภาพดีกว่ามาก | แพง กินไฟ ต้องเชื่อม Pi↔ESP32 |
| C | เริ่มด้วยภาพจากมือถือก่อนเลือกกล้อง | ลดเสี่ยง | (ผู้ใช้ไม่เลือก) |

**ผู้ใช้เลือก A** **[คุณเลือก]**
ความเสี่ยงที่ยอมรับ: ถ้าภาพ ESP32-CAM ไม่พอ ต้องย้ายไป B — ลดความเสียหายได้ด้วยการทำ Server ให้รับภาพผ่าน API เดียว (`ภาพ + สถานี + รอบ`) ไม่ผูกกับชนิดกล้อง **[ผมเลือก]**

## 5. สถาปัตยกรรม
```
ESP32 DevKit V1  ── Wi-Fi ──►  Python Server (hosting ฟรี)  ──► Claude API
 (มอเตอร์, IR, RFID,            ├─ รับภาพ/สถานะรถ                  (วิเคราะห์ภาพ,
  ultrasonic, servo, แบต)       ├─ OpenCV: กรองภาพ/ตัดใบ            สรุปรายงาน, Q&A)
ESP32-CAM ──── Wi-Fi ────────►  ├─ บันทึก Postgres + object storage
                                ├─ Dashboard (เว็บ) ◄── แท็บเล็ตบนรถ
                                └─ แจ้งเตือน Telegram
```
- **ฐานข้อมูล: PostgreSQL ฟรี** (เช่น Supabase/Neon) + ภาพใน object storage เก็บเฉพาะ URL ในตาราง **[ผมเลือก]** เพราะดิสก์ของ hosting ฟรีไม่ถาวร
- ข้อมูลเป็นตาราง (สถานี, รอบ, เวลา, มุมกล้อง, ผล, แบต, แจ้งเตือน) → "RAG" = ดึงแถวด้วย SQL แล้วให้ Claude สรุป ไม่ใช้ vector DB **[ผมเลือก]**

### ตำแหน่งสถานีจาก RFID **[คุณเลือก]**
- ตาราง `stations`: `rfid_uid` (unique), `ชื่อสถานี`, `ตำแหน่ง/รายละเอียด`, `map_x`/`map_y` (จุดบนแผนผังโรงเรือนสำหรับ Dashboard), `ลำดับในเส้นทาง`, `active` — กรอกครั้งเดียวตอนติดตั้งแท็ก
- **จำนวนสถานี**: เริ่มที่ **3** ตามเอกสาร แต่ไม่ฝังเลข 3 ในโค้ด — จำนวน = แถว `active` ในตาราง `stations` **[ผมเลือก]**
- **Home** มีแท็ก RFID ของตัวเอง (ประเภท `home`) ไม่นับเป็นสถานีตรวจ
- **รอบตรวจครบ** เมื่อทุกสถานี `active` มีผลบันทึกของรอบนั้น; สถานีที่ขาด → ทำเครื่องหมายรอบ "ไม่ครบ" และแจ้งเตือน
- ESP32 อ่าน UID แล้วส่งให้ Server; Server แปลง UID → สถานี เอง ไม่ฝังชื่อสถานีไว้ในเฟิร์มแวร์ (เปลี่ยนชื่อ/ย้ายแท็กได้โดยไม่แฟลชบอร์ด) **[ผมเลือก]**
- ทุกภาพ ผลวิเคราะห์ และการแจ้งเตือน อ้างถึง `station_id` + `round_id` เสมอ
- UID ที่ไม่รู้จัก → บันทึกเป็น "แท็กไม่รู้จัก" และแจ้งเตือนระบบขัดข้อง ไม่เดาสถานี
- Dashboard แสดง "สถานีปัจจุบัน" จากแท็กล่าสุดที่อ่านได้

### รองรับผักหลายชนิดในอนาคต **[คุณเลือก]**
- ตาราง `crops`: `ชื่อผัก`, `อาการที่ตรวจ` (รายการ label เช่น ใบเหลือง, จุดน้ำตาล), `prompt` สำหรับ Claude, `เกณฑ์แจ้งเตือน`, `หมายเหตุธรรมชาติ` (เช่น ใบแก่เหลืองปกติ, tipburn ของกรีนคอส)
- `stations.crop_id` ผูกสถานีกับชนิดผัก — ต่างสถานีปลูกต่างผักได้
- Server สร้าง prompt จากแถวใน `crops` (ไม่ฝัง prompt ของกรีนคอสในโค้ด) และตรวจว่า label ที่ Claude ตอบอยู่ในรายการของผักนั้น **[ผมเลือก]**
- ผลวิเคราะห์เก็บ `crop_id` ณ เวลาตรวจ เพื่อให้แนวโน้มย้อนหลังไม่ปนกันเมื่อสถานีเปลี่ยนผัก
- เพิ่มผักใหม่ = เพิ่มแถว + ชุดภาพทดสอบของผักนั้น ไม่แก้โค้ด; **ข้อจำกัด:** อาการใหม่ที่ไม่ใช่ "เหลือง/จุดน้ำตาล" ยังต้องตรวจความแม่นยำใหม่ทุกครั้ง ไม่ใช่แค่เพิ่ม label

## 6. พฤติกรรมของแต่ละส่วน
**วิเคราะห์ภาพ (Claude)** **[ผมเลือก]**
- ให้ตอบเป็นรูปแบบคงที่: `{label: ปกติ|ใบเหลือง|จุดน้ำตาล, ความมั่นใจ, หมายเหตุสั้น}`
- ความมั่นใจต่ำ → ถ่ายซ้ำ (ตามจำนวนครั้งที่กำหนด) แล้วทำเครื่องหมาย "ควรให้คนตรวจ"
- OpenCV เป็นด่านหน้า: ทิ้งภาพเบลอ/แสงไม่เหมาะสม ตัดบริเวณใบ ก่อนส่ง Claude เพื่อไม่เสียค่าภาพเสีย

**ถามตอบบน Dashboard** **[ผมเลือก]**: Claude เรียกฟังก์ชันคิวรีที่เราเขียนไว้ล่วงหน้า (เช่น ผลล่าสุดของสถานี, แนวโน้มรายสถานี N วัน) ไม่ให้เขียน SQL เอง

**รายงานประจำรอบ**: Server รัน SQL สรุป (นับอาการต่อสถานี เทียบรอบก่อน) → ส่งตัวเลขให้ Claude เขียนรายงานและแนวโน้ม

**แจ้งเตือน**: อาการเกินเกณฑ์, แบตต่ำ, ระบบขัดข้อง พร้อมภาพ และบันทึกสถานะการส่ง
- ช่องทาง: **Telegram** เป็นค่าเริ่มต้น **[ผมเลือก]** (ผมเข้าใจว่า LINE Notify ถูกยกเลิกแล้ว ส่วน LINE Messaging API ต้องตั้ง official account — ยังไม่ได้ตรวจ)

**ฝั่งรถ** (ตามเอกสาร): เดินตามเส้น IR → หยุดที่แท็ก RFID → หมุนกล้อง หยุดนิ่ง → ถ่าย; หยุดเมื่อมีสิ่งกีดขวาง; วัดแบตส่งเข้า ESP32

## 7. ลำดับการสร้าง (ตามเอกสาร)
1. กำหนดชนิดผัก เกณฑ์วัดผล และ schema ฐานข้อมูล
2. กล้อง → Server → OpenCV → Claude → บันทึก ให้ครบ **1 สถานี** (ทดสอบกับภาพจริงจากแปลงก่อนกำหนดขอบเขต)
3. Dashboard + แจ้งเตือน
4. รถเดินตามเส้น + RFID + หยุดเมื่อมีสิ่งกีดขวาง
5. ชุดหมุนกล้อง + วัดแบตเตอรี่
6. ต่อครบ 3 สถานี + Claude สรุปผล + ทดสอบทั้งระบบ

เกณฑ์ผ่านขั้น 2: เก็บภาพจริง 20–30 ใบ ให้คนติดป้ายกำกับ แล้ววัดว่า Claude ตอบตรงกันกี่ %

## 8. ที่เหลือให้ผู้สร้างตัดสิน (ค่าเริ่มต้นของผม)
- ชนิดผัก: **กรีนคอส (green cos)** — ผู้ใช้บอกว่า "น่าจะ" จึงยืนยันอีกครั้งก่อนเขียน prompt **[คุณเลือก]**
  - ใบแก่รอบนอกเหลืองตามธรรมชาติได้ และขอบใบไหม้สีน้ำตาลจาก tipburn (ขาดแคลเซียม/ร้อน) อาจเหมือนโรค → prompt ต้องบอก Claude ให้แยก/ระบุหมายเหตุ และชุดภาพทดสอบต้องมีตัวอย่างพวกนี้ **[ผมเลือก]** (ความรู้ทั่วไป ควรให้ผู้ปลูกยืนยัน)
- ชื่อ hosting ฟรี — เลือกตอนเริ่มขั้น 2 หลังตรวจเงื่อนไขปัจจุบัน
- รุ่น Claude: Haiku 5.5 สำหรับถามตอบ/สรุป; รุ่นสำหรับวิเคราะห์ภาพตัดสินหลังทดสอบความแม่นยำและค่าใช้จ่าย
- จำนวนครั้งถ่ายซ้ำ (เริ่มที่ 2), จำนวนมุมกล้องต่อสถานี, เกณฑ์แจ้งเตือน (เริ่มที่ "พบผิดปกติ ≥ 1 ใบที่ความมั่นใจสูง") — ปรับหลังทดสอบจริง
- เทียบ ESP32-CAM บนรถ: ถ้าภาพไม่พอ ให้ย้ายไปแนวทาง B

## 9. ความเสี่ยงที่รู้อยู่แล้ว
- ภาพ ESP32-CAM อาจไม่พอ (ลดผลกระทบด้วย API กลาง)
- Wi-Fi/อินเทอร์เน็ตในโรงเรือนหลุด → ต้องมีคิวเก็บภาพบนรถหรือถ่ายซ้ำรอบถัดไป (ยังไม่ได้ออกแบบ)
- ค่า Claude API เพิ่มตามจำนวนภาพ
- ความแม่นยำของ Claude กับผักและแสงจริงยังไม่รู้จนกว่าทดสอบ
